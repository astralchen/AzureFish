# 数据生命周期、迁移与异常恢复

> **状态：设计阶段，尚未接入应用。** 本文为后续开发约束；尚未实现数据库接入、迁移、后台任务或搜索。返回 [文档入口](README.md)。

## 1. 账号作用域与文件保护

打开顺序为：取得已认证账号与环境 → 计算账号目录键 → 检查受保护数据与 Keychain 可用 → 取得原账号密钥 → 创建或打开 SQLCipher 数据库 → 核对 account_store_meta → 执行迁移 → 恢复任务 → 启动观察和同步。元数据与当前账号或环境不符时拒绝打开，不能将目录误认当作空库覆盖。

身份由 [客户端 SessionCoordinator](../Authentication/client-integration.md) 接收并验证 AzureFishServer 的 AuthResponse 后提供。以 environment_id＋稳定 user_id 隔离数据，服务端会话确认的安装 device_id 与本机存储 UUID 各司其职，不能以昵称、登录账号名或 Apple 邮箱作为目录身份。访问／刷新凭据只进入 Keychain，不写入业务库；离线读取仍需符合客户端认证恢复规则，不能把磁盘上有旧账号库当作在线鉴权成功。真实账号首次登录不会接管 local-demo 数据。

AccountStore 为每次登录会话分配内存 generation。所有网络、文件、数据库观察和后台任务携带 generation；退出登录先使 generation 失效，再取消任务及观察、等待正在提交的事务结束、关闭数据库。用户切换回原账号时仍重新创建 generation。登录失效不会自动删除磁盘上的消息或草稿。

数据库及 WAL／SHM、原件和 staging 采用 `completeUntilFirstUserAuthentication`。保护不可用时暂停任务并在系统通知可访问后恢复，不能将 SQLite I/O 错误一概认定为库损坏。此保护方式支持设备首次解锁后的后台访问；不等同于应用独立密码加密。认证令牌由登录模块使用 Keychain 管理，不写消息表。

明确“清除此账号本地数据”后，停止工作流并关闭句柄，删除账号业务目录及账号缓存目录；不删除其他账号和环境。重新登录后按服务端保留范围恢复，未上传消息和本机草稿无法通过服务器自动找回。首期不提供跨设备密钥恢复或自定义导出备份；账号库、媒体和缓存均排除系统备份，仅保留同设备加密迁移备份及对应旧钥。清理本地数据须同时处理该账号备份，最后删除存储密钥，见 [安全规范](../Security/README.md)。未来数据库导出必须用一致性备份 API，不能只复制正在使用的 main.sqlite 而遗漏 WAL。

## 2. 资源所有权与崩溃恢复

### 三个所有权阶段

| 阶段 | 所有者 | 清理条件 |
| --- | --- | --- |
| 编辑、相册导入或临时预览 | PageAttachmentStore | 页面取消或销毁；被正在保存的工作租用时延迟清理 |
| 已保存草稿或发送队列消息 | 账号级 MediaRepository | 没有草稿、消息、任务与活动访问租约后才允许回收 |
| 可重建缩略图、已下载缓存 | 账号缓存服务 | 可按预算淘汰，但保留资源身份及重新获取能力 |

入库前在受控导入流程读取原文大小、摘要及类型，以账号媒体密钥加密到 staging，认证回读后原子 rename 密文到目标目录，再提交 media_asset、media_resource、引用关系和业务行。导入始终使用新资源身份或受控复用，不能覆盖已引用原件。Live Photo 要求照片与 paired_video 全部完成，才可以将整个逻辑 asset 交付为 ready；单独照片不能冒充完整 Live Photo。

若文件准备完成但数据库回滚，最多留下无引用文件，不允许数据库提交一个尚不存在的 ready 文件。定期对照已知路径回收孤立文件；扫描宽限期默认 24 小时，并避开当前导入 registry 与活动租约。staging 的任务进度仅对本次会话有效，重启后无持久引用的 staging 文件可按宽限期清理。

数据库只存相对路径与 remote_object_key。解析器拒绝绝对路径、空组件、`.`、`..`、反斜杠替代路径、目录逃逸及穿越符号链接；路径归一后必须仍位于当前账号根目录。文档中的相对路径 CHECK 仅是第一层防御，不能替代文件解析器。`cache/` 前缀指向当前账号的 Caches 子目录，其余路径指向 Application Support。

### 状态与回收

资源本机状态：absent → staged → ready；文件丢失变 missing，可下载恢复后回 ready；进入 deleting 时不能获得新引用。durable 原件不会因为空间预算自动淘汰，cache 资源可变 absent。远程对象是否存在与本地文件状态分别判断。

资源 GC 先在事务中确认无 message_attachment、draft_attachment、活动 transfer_job、非 GC 的资源维护任务，并取得账号级独占回收租约；然后标记 deleting。文件删除在事务外进行，删除成功后事务删除 GC 任务自身、已结束传输记录、资源及 asset。GC 任务自己的外键不能阻止最终删除，因此须在该事务先移除任务。文件删除失败保留状态和可重试任务，不提前标记成功。

新建引用和读取租约都与账号级资源协调器串行核对 deleting 状态，不能在“检查无引用”和“物理删除”之间插入新引用。首期只有主应用进程拥有存储；未来加入 App Extension 时，必须增加跨进程协调，不能仅复用内存租约。

启动时分别检查：无引用文件、ready 但文件缺失、deleting 未完成、租约过期任务。下载恢复是可选能力：缺失文件若没有 remote_object_key，显示不可恢复／重新选择，不伪造空附件；原件不能被缩略图替换。

## 3. 持久任务与迟到结果

outbox_operation 管业务命令，transfer_job 管单资源上传／下载，maintenance_job 管 GC、缩略图和索引重建。索引单实体失效由 search_dirty 表承担，不为每次键入创建独立任务。

任务统一状态：queued → running → succeeded；临时失败 running → retry_wait → running；不可恢复失败 → failed；用户撤销 → cancelled。仅 failed 的显式重试能重新进入 queued，必须创建新 lease token；业务幂等 ID 不变。领取 running 时同时写入 lease_token、租约截止、attempt_count。完成、错误回写及续约都要求任务仍为 running 且 token 相等，旧回调不可覆盖新尝试。

默认租约 60 秒，活动工作每 20 秒续约；长上传必须续约。进程重启后旧进程任务不可能继续在本机执行，但服务端可能已接受，恢复为 queued 后继续使用原幂等身份。应用存活期间只有到期且未续约任务才能再次领取。后台运行时间不足时让出工作，不能依靠定时器保证 iOS 无限执行。

同一资源同方向只有一个 transfer_job；重新下载时更新原行并递增 generation。已完成传输任务可删除，业务引用负责继续保留资源。业务 outbox 成功记录至少保留到消息确认合并，随后可按维护策略清理；幂等的最终屏障仍是服务端和 message 唯一约束。

阅读命令可以取消尚未 running 的较低水位任务，再插入更高水位命令；已开始的低水位回包按 max 合并，不使状态倒退。维护任务重复调度复用 dedupe_key 的原行，重置状态前确保旧租约已失效。

## 4. 草稿与当前工程迁移

| 当前实现 | 后续接入方式 | 兼容要求 |
| --- | --- | --- |
| ChatViewModel.messages / nextMessageID | MessageRepository 提供观察与分页，local_id 映射为稳定展示身份 | 列表刷新、菜单目标、媒体组项目身份不因 ACK 改变 |
| MessageSending 本地模拟 | 替换为持久入队和模拟传输适配器 | 原 send 成功不能直接映射为真实对端送达 |
| MessageHistoryLoading | 数据库优先分页；需要时同步缺口再发布快照 | 保留 38／20 页大小、迟到请求代次检查和滚动锚点 |
| PageAttachmentStore | 保留临时编辑职责；提交时转交账号存储 | deinit 只删除页面临时文件，不能删除持久原件 |
| ChatDraftStore / ChatDraftSnapshot | 按 revision 写入 draft 和 draft_attachment | 保留富文本、文档顺序、媒体组、语音、空白正文和 Live Photo 配对 |
| SampleChatHistory / ConversationPreviewData | 继续作为独立演示／测试来源 | 不自动导入真实账号、不写网络 outbox |

存储模型只包含 Foundation／Sendable 值类型，不引用当前带 iOS 26 限制的 UI 类型。现有 Message.id 的 Int 接口可通过适配层从 Int64 local_id 转换；不能以页面新分配 ID 重新编号整个持久历史。

### 一次性旧草稿导入

1. 只在 `local-demo` 本地演示账号中导入 Application Support/ChatDrafts；旧目录没有可靠真实账号归属，禁止归给首次登录的真实用户。
2. 按旧草稿版本和清单摘要识别源，源目录只读。校验相对路径、资源完整性及 Live Photo 配对；部分缺失沿用现有可恢复项策略并记录提示，损坏清单保留原文件。
3. 将有效资源加密写入演示账号持久目录，保持原附件身份和顺序；转换载荷为 asset_id 引用。
4. 在同事务写入草稿、引用和 legacy_import；若已有同 source_key＋source_digest 成功记录则跳过。目标已有用户新草稿时不覆盖，记录冲突供后续迁移入口处理。
5. 完整恢复验证成功后才允许后续清理旧副本。本次设计默认保留旧副本，不因一次自动启动删除旧数据。

旧内存消息在进程退出后没有持久来源，不声明可以迁移。演示与测试注入使用隔离临时账号库，不能把预览数据写入正式用户目录。

### 保存并发

草稿保存采用 expected_revision 乐观并发，与 conversation_local_state.draft_revision 比较；从未保存的会话初值为 0。每次保存或删除都令该持久序列＋1，草稿存在时 draft.revision 与它相等；删除草稿行也不能清零序列，读取空草稿仍返回当前 revision。保存到空草稿等同于删除，但同样检查 revision。发送入队只在预期 revision 匹配时删除其草稿并递增序列；期间用户已输入的新草稿必须保留。文件复制先完成再开启事务，数据库冲突时回收此次新建无引用文件。

## 5. 数据库与内容版本迁移

数据库物理结构版本由 GRDB DatabaseMigrator 的迁移账本维护，不另外手工写一套 user_version 和 migration_meta 竞争权威。account_store_meta 用于账号和本地序列元数据，不替代迁移账本。

每次结构迁移追加不可变迁移名；禁止修改已经发布的迁移内容。能放进事务的结构修改同事务执行，大数据回填采用“新增可兼容字段 → 记录进度分批回填 → 读取兼容 → 后续收紧约束”。FTS 重建与复杂文件移动不阻塞一个长期 schema 事务。

迁移前核对磁盘空间并创建同设备一致性加密数据库备份，保留对应旧钥；迁移失败保留原库与备份、停止进入写业务，不自动清空重建。应用降级发现未知 schema 版本时拒绝写入，提示升级；不能用旧版本代码覆盖新字段。备份保留与清理仅针对同账号，媒体的完整导出恢复需另立备份方案。

schema 版本、content_schema_version、草稿版本、网络协议版本和 tokenizer_version 相互独立。未知 payload 保留原始 JSON；已知类型解码失败应将该消息标为不可展示并保留诊断，不导致整段聊天无数据。不可解析的协议信封属于批次错误，不能与未知内容类型混为一谈。

## 6. 搜索索引

首期使用 search_document 作为外部内容表，FTS5 的 rowid 与 document_id 对齐。投影插入／更新／删除与 FTS 维护同事务；正文业务写入只标记 search_dirty。联系人索引包含昵称和备注，会话索引包含群名，消息索引包含正文、文件名和已存在的语音转写；不首期引入 OCR、拼音、语义向量或全文云搜索。

### 分词 v1

简中／繁中都使用 Han 分词规则，首期不做跨简繁同义转换；界面语言变化不修改消息或重建另一份明文索引。原文始终原样保存在加密库；单独生成 NFKC 规范化、大小写折叠文本供搜索。规范化不能反写用户消息。中文 Han 字符输出单字 token 和相邻双字 token；英文／阿拉伯文连续字母数字及附着组合标记输出词 token，不去掉阿拉伯语区别性标记。标点分隔词，首期不支持仅 emoji 的检索。

token 使用 ASCII 安全编码：单字加 `h` 前缀＋码点十六进制，双字加 `b` 前缀＋两个以 `z` 分隔的码点，其他词加 `w` 前缀＋规范化 UTF-8 字节十六进制。文档和查询使用完全相同算法，token 以空格分隔，FTS 使用 ascii tokenizer。用户文本从不作为原始 MATCH 表达式执行。

中文一字查询使用单字 token，多字查询使用相邻双字的 AND 候选，再对 normalized_text 做连续子串复核，避免“字符齐全但次序不同”误命中。英文／阿拉伯文采用整词匹配；多段查询为 AND。没有 token 的查询返回空结果并提示输入文字，不扫描百万行兜底。

每次失效从 account_store_meta.search_generation 分配单调递增 generation，再 upsert search_dirty。后台读取实体与 generation，在事务外生成 token；提交时同时检查 dirty generation 和当前删除／清空状态，匹配才更新投影并移除该条 dirty。全局序列不能在删除 dirty 行后重置，避免旧任务与新一轮失效发生 ABA 冲突。

搜索候选始终回查 message、tombstone、clear_through_seq、revoke_state 和 content 版本。被删除／撤回的候选即使索引尚旧也不能显示。页面显示时再核对当前状态，索引中的 normalized_text 不能绕开回查直接充当正文。索引重建按 local_id 范围分批推进，期间正常写入持续标记 dirty；最后消费残留 dirty，而不是用重建开始时的旧快照覆盖新增消息。

tokenizer_version 变化或系统 Unicode 规范化行为版本变化时重建整个搜索投影；结果排序首期为消息服务端时间降序、local_id 打破平局。会话、发送者、类型和日期过滤通过主表执行，不能以缓存字段绕过权限／删除状态。索引可以删除重建，业务库与未上传内容不能因搜索故障删除。

## 7. 异常矩阵

| 异常 | 必须采取的行为 | 不允许的行为 |
| --- | --- | --- |
| 磁盘满 | 回滚数据库事务；保留旧草稿；报告失败并停止继续扩张 staging | 先显示持久化成功再静默丢失 |
| 数据受保护 | 暂停访问，等待解锁可用通知 | 当作损坏删库 |
| 文件丢失 | 标记 missing，有远程键时允许重下；否则显示不可恢复 | 伪造 ready 或空文件 |
| 正文 payload 未知 | 保存原始载荷，使用兼容占位 | 丢弃消息身份或阻止历史翻页 |
| 数据库结构损坏 | 停写，保留原库／WAL及诊断副本，用只读检查确认后由恢复流程处理 | 把 GRDB 当作自动修复框架或无提示重建 |
| FTS 错误 | 暂停搜索并重建索引，核心消息读写按数据库健康程度继续 | 直接清空消息库 |
| 任务重复执行 | 依赖幂等键、唯一约束和租约 token 合并 | 每次重试新建消息 |
| 账号切换迟到回包 | 校验旧 generation 后丢弃 | 写入当前活跃账号 |

运行诊断只记录错误码、耗时、任务类型和脱敏身份，不记录消息正文、认证 token、签名 URL 或完整用户路径。百万消息性能、损坏恢复和系统保护的真实表现均需按 [验收计划](validation.md) 单独验证。
